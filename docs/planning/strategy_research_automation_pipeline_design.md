# JQ 社区策略研究自动化流水线设计

更新日期：2026-08-15<br>
状态：设计方案，尚未完整实现<br>
适用范围：`strategies/etf_rotation/`、`backtest_executor/` 以及 JQ 研究环境中的策略回测与参数研究

## 1. 文档目的

本设计希望把下面这条以手工操作为主的研究路径，逐步改造成可恢复、可追溯、可验证的半自动流水线：

1. 在 JQ 社区发现有研究价值的帖子、策略和研究材料；
2. 筛选候选并取得可研究的策略源码；
3. 审计策略逻辑、数据口径和回测可信度；
4. 在尽量不改变原策略语义的前提下完成参数化和性能优化；
5. 在 JQ 研究环境中做短区间冒烟回测；
6. 跑通后执行低成本、自适应的参数搜索；
7. 对晋级参数做完整区间、样本外和鲁棒性分析；
8. 根据可追溯的实验数据生成 Markdown 研究文档。

目标不是让程序无监督地下载任意社区代码并立即大规模回测，而是把重复劳动自动化，并在源码引入、语义修改和最终结论处保留人工确认。

## 2. 当前工程基线

### 2.1 已有能力

当前 `backtest_executor` 已经覆盖参数研究链路的后半段骨架：

- 从策略源码提取 `EXECUTION_` 参数默认值；
- 使用 AST 计算忽略参数初值的策略逻辑 hash；
- 向策略源码注入完整参数；
- 通过 `create_backtest()` 提交回测；
- 通过 `get_backtest()` 轮询状态并记录回测 ID；
- 使用 `mapper.json` 跨轮次去重；
- 支持 Grid、Random、List、Sensitivity 四种参数生成方法；
- 保存 `get_risk()` 的部分汇总指标；
- 可从 `get_period_risks()` 或 `get_results()` 提取年度收益。

### 2.2 当前缺口

工程还缺少以下端到端能力：

- 社区帖子候选台账和来源追踪；
- 原始源码的不可变留存；
- 面向 JQ 策略的静态审计和试跑前门禁；
- 原版、参数化版和性能优化版之间的等价验证；
- 回测完整数据包的本地缓存；
- 根据已完成结果决定下一组参数的自适应搜索；
- 参数平台、PBO、DSR、持仓归因和换仓效果分析；
- 从实验事实生成研究文档。

### 2.3 自动化前应先修正的执行风险

以下是现有实现事实，不代表已经修复：

1. `executor.py` 使用模块级 `Default_Back_Id`，YAML 中的 `strategy.base_id` 当前只作记录，未传给执行器。
2. 任务 ID 目前没有覆盖策略逻辑 hash、锚点策略 ID、基准、`use_credit`、Python 版本和成本口径，存在错误复用历史结果的可能。
3. 策略逻辑变化后当前提示删除 `mapper.json`；目标行为应是自动建立新策略版本并保留旧实验。
4. `mapper.json` 读取失败时当前会静默返回空台账；目标行为应保留原文件并明确失败。
5. 非 JQ 环境且无法取得 `get_backtest()` 时，`analyzer.py` 当前会生成随机模拟指标；正式分析必须明确失败，模拟数据只能通过显式测试模式启用。
6. 随机搜索可能重复采样，只依靠执行器事后去重，且没有固定随机种子和自适应反馈。
7. 回测完成后当前只立即保存部分 `get_risk()` 指标，没有形成可离线复盘的完整数据包。

## 3. 已确认的 JQ 平台约束

### 3.1 真实锚点策略 ID

当前 JQ 研究环境已经实测确认：调用 `create_backtest()` 时，即使传入完整的 `code` 参数，也仍然必须传入一个真实存在且当前账号有权访问的 `algorithm_id`。

因此：

- `algorithm_id` 不能省略；
- 不能随机生成；
- 可以长期复用任意一个真实可用的 JQ 策略作为锚点；
- 实际回测逻辑由传入的 `code` 决定；
- 锚点策略 ID 与当前策略逻辑身份不是同一个概念。

建议将配置名称从含义模糊的 `base_id` 调整为：

```yaml
jq:
  anchor_algorithm_id: "6e21bbaee8cc3f8423def84436a2bf49"
```

其中：

- `anchor_algorithm_id` 用于满足 JQ 平台的回测创建要求；
- `strategy_logic_hash` 用于标识本次实际运行的策略逻辑；
- 两者都应写入实验元数据；
- 为兼容现有配置，可以继续使用当前真实 `Default_Back_Id` 作为默认值，但允许 Notebook 参数或 YAML 覆盖。

### 3.2 回测结果接口

JQ 官方文档列出的 `get_backtest(backtest_id)` 数据包括：

- `get_status()`：回测状态；
- `get_params()`：实际回测参数；
- `get_results()`：逐日累计收益和基准收益；
- `get_positions()`：逐日持仓；
- `get_orders()`：交易明细；
- `get_records()`：策略通过 `record()` 主动记录的数据；
- `get_risk()`：全区间风险指标；
- `get_period_risks()`：分周期风险指标。

项目本地 API 文档还记录了 `get_balances()`。公开文档与实际研究环境可能存在版本差异，因此实现采集器时必须：

- 用能力探测判断方法是否存在；
- 允许可选字段缺失；
- 保存实际返回字段列表和采集时间；
- 不根据未验证的字段静默推断结果。

参考资料：

- [聚宽官方 API PDF](https://cdn.joinquant.com/help/img/JoinQuantAPI.pdf)
- [`../reference/joinquant/official/strategy-api.md`](../reference/joinquant/official/strategy-api.md)

## 4. 目标流水线

```text
社区发现
  → 候选台账
  → 源码静态审计
  → 参数化与性能改造
  → 默认参数等价验证
  → JQ 短区间试跑
  → 自适应参数搜索
  → 完整区间与鲁棒性验证
  → Markdown 研究文档
```

每个候选策略使用显式状态机：

```text
discovered
→ source_saved
→ reviewed
→ adapted
→ preflight_passed
→ smoke_passed
→ searching
→ validated
→ documented
```

失败不能通过删除文件或覆盖状态隐藏。建议记录：

```text
rejected / preflight_failed / smoke_failed / search_failed
```

并保存失败阶段、错误摘要、JQ 回测 ID、重试次数和最后更新时间。

## 5. 社区发现与候选筛选

### 5.1 发现方式

社区发现层负责生成候选，不负责直接决定策略是否值得回测。它可以从公开搜索结果和帖子详情页提取：

- 标题、作者、发布日期和 URL；
- 策略类型和主要机制；
- 浏览、收藏、回复等热度信息；
- 是否包含源码、研究文件或可复现说明；
- 帖子声称的区间、收益、回撤和成本口径；
- 引用的原始策略和后续改进帖。

社区页面可能有登录、动态加载、地区限制和反自动化机制。该层应允许浏览器辅助导入和手工 URL 导入，不把无人值守的大规模抓取作为主路径。

### 5.2 初始发现入口

以下帖子可作为第一批发现入口或研究候选，但尚不代表已经完成源码审计：

- [社区策略汇总分类](https://www.joinquant.com/community/post/detailMobile?postId=51024)：候选发现索引；
- [ETF 轮动策略系列之——低相关性策略](https://www.joinquant.com/community/post/detailMobile?postId=64315)：波动率、相关性和趋势周期均适合参数化；
- [ETF 动量轮动策略优化](https://www.joinquant.com/community/post/detailMobile?postId=50224)：可作为现有动量策略的对照，需重点检查止盈止损参数过拟合；
- [对 ETF 轮动策略的看法](https://www.joinquant.com/community/post/detailMobile?postId=24430)：适合转化为交易成本、无意义调仓和历史反复优化的审计规则；
- [避免未来数据](https://www.joinquant.com/community/post/detailMobile?postId=23804)：源码预检的官方规则来源。

### 5.3 候选评分

帖子声称的收益率不能作为主要排序依据。建议候选评分覆盖：

| 维度 | 重点问题 |
| --- | --- |
| 机制清晰度 | 收益来源能否用明确的市场机制解释 |
| 源码完整性 | 是否具备完整、可解析、可复现的源码 |
| 数据可信度 | 是否存在未来数据、当前成分回填或幸存者偏差 |
| 交易真实性 | 成本、滑点、停牌、涨跌停处理是否合理 |
| 参数可研究性 | 参数是否具有清晰含义和合理范围 |
| 样本覆盖 | 回测区间是否覆盖多种市场状态 |
| 策略差异性 | 与仓库现有策略是否只是换名或轻微改参 |
| 计算成本 | JQ API 调用、分钟循环和日志量是否可控 |

浏览、收藏和回复数只用于发现，不直接证明策略有效。

### 5.4 人工确认

候选进入源码改造前保留一次人工确认，至少核对：

- 是否确实值得投入回测资源；
- 源码是否允许用于当前本地研究；
- 是否需要保存作者和原帖引用；
- 是否存在不能自动接受的依赖、附件或数据来源。

## 6. 候选策略资产结构

建议每个策略候选使用独立目录，并把原始源码与生成物分开：

```text
research/<candidate_id>/
├── candidate.yaml       # 来源、作者、URL、评分、状态
├── source/
│   └── original.py      # 原始源码，只读留存
├── strategy/
│   ├── adapted.py       # 参数化版本
│   └── optimized.py     # 性能优化版本
├── changes/
│   ├── adapt.patch      # 参数化改动证据
│   └── optimize.patch   # 性能优化改动证据
├── search.yaml          # 参数空间和搜索预算
├── runs.json            # 实验台账或其索引
├── data/                # JQ 回测数据包
└── report.md            # 最终研究文档
```

最小追溯信息包括：

- 原帖 URL、作者和获取时间；
- 原始源码 hash；
- 参数化版本逻辑 hash；
- 性能优化版本逻辑 hash；
- 每项语义修改的理由；
- 使用的 JQ 锚点策略 ID；
- 回测环境和实验配置指纹。

## 7. 源码审计、参数化和性能优化

### 7.1 静态审计

进入 JQ 回测前，自动检查：

- Python 语法和 AST 是否可解析；
- 是否存在 `initialize(context)` 等必要入口；
- 定时函数引用是否存在；
- 是否开启或兼容 `avoid_future_data`；
- `get_price()`、`history()`、`attribute_history()` 的时间参数是否可能读取未来数据；
- 是否使用当前 ETF 列表回填历史；
- 是否缺少真实交易成本和滑点配置；
- 是否依赖外部文件、网络、共享函数或未包含模块；
- 是否有大量循环内 JQ 数据请求；
- 是否有高频日志和无必要的分钟级定时任务；
- 是否存在无法自动参数化的动态表达式。

静态审计只能发现风险，不能证明策略没有未来数据或逻辑错误。

### 7.2 参数化规则

机械参数化可以自动完成：

- 把可调字面量提取为 `EXECUTION_` 全局变量；
- 为参数生成短名、默认值、类型和候选范围；
- 生成对应 YAML；
- 增加回测日志开关；
- 增加统一的 `record()` 诊断字段；
- 注入后重新执行 AST 和语法检查。

以下属于语义修改，必须保留人工确认：

- 改变选股、评分、止损或调仓条件；
- 改变交易时间和频率；
- 修改 ETF 池或市场范围；
- 改变成本和成交假设；
- 用新的数据替换原数据来源。

### 7.3 回测性能优化

在不改变默认参数行为的前提下，优先进行：

- 将循环内逐只 `attribute_history()` 合并为批量 `get_price()`；
- 缓存同一时点、相同区间和字段的重复查询；
- 合并重复计算的动量、波动率、成交量和均线；
- 回测模式关闭大量逐仓位日志；
- 只在调仓日或每日一次调用研究诊断 `record()`；
- 删除没有业务作用的空回调和重复定时任务；
- 在不改变执行语义时减少分钟级数据请求。

不能为了速度静默关闭未来数据检查、改变调仓时刻、删掉交易限制或缩短正式验证区间。

### 7.4 等价验证

原版和机械改造版必须在相同默认参数、相同区间和相同成本口径下比较：

- 是否均成功完成；
- 逐日累计收益是否一致或在解释后的容差内；
- 订单数量和关键成交是否一致；
- 每日持仓是否一致；
- 最大回撤、总收益等关键指标是否一致；
- 回测运行时间是否改善。

如果性能优化改变结果，必须明确记录原因，不能把结果变化归类为单纯性能提升。

## 8. JQ 试跑门禁

每个新策略先执行低成本试跑，不直接开始参数搜索。

建议顺序：

1. 本地语法、参数注入和静态审计；
2. 选择覆盖实际交易的 3 至 6 个月区间；
3. 使用默认参数提交一个 JQ 回测；
4. 确认状态为 `done`；
5. 检查收益曲线、交易次数、持仓和风险指标是否存在；
6. 检查是否有异常空仓、零交易、极端换手或 API 返回缺失；
7. 通过后执行较长基准回测；
8. 基准通过后才允许生成参数搜索任务。

冒烟通过不代表策略有效，只代表代码、数据依赖、交易流程和结果采集已经跑通。

## 9. 实验身份与持久化

实验不能只由参数 MD5 标识。建议任务指纹至少覆盖：

```python
execution_context = {
    "strategy_logic_hash": strategy_logic_hash,
    "params": full_params,
    "anchor_algorithm_id": anchor_algorithm_id,
    "start_day": start_day,
    "end_day": end_day,
    "frequency": frequency,
    "initial_cash": initial_cash,
    "benchmark": benchmark,
    "python_version": python_version,
    "use_credit": use_credit,
    "cost_profile": cost_profile,
}
```

策略逻辑变化时：

- 创建新的策略版本或实验目录；
- 不删除旧 `mapper.json`；
- 允许跨版本查看，但默认禁止直接合并排序；
- 只有明确确认成本、区间和代码口径一致时才可比较。

台账写入应使用临时文件加原子替换，并在解析失败时保留损坏文件和报错，不能静默重建为空台账。

## 10. 回测数据包

### 10.1 全部回测保存

- 实际参数和回测配置；
- `get_status()`；
- `get_params()`；
- `get_risk()`；
- `get_results()`；
- `get_period_risks()`；
- `get_records()`；
- 数据采集时间和实际字段列表。

其中 `get_results().returns` 是累计收益。转换日收益时使用：

```python
daily_return = (1 + cumulative_return).pct_change()
```

首日收益需要单独处理。

### 10.2 晋级候选保存

- `get_orders()`；
- `get_balances()`，如果当前研究环境支持。

### 10.3 最终候选保存

- `get_positions()`；
- 完整持仓归因和换仓分析所需行情。

这种分层可以避免每组回测都下载体量较大的订单和持仓数据。

### 10.4 `record()` 诊断约定

策略应按需记录能够解释参数行为的内部状态，例如：

```python
record(
    candidate_count=len(candidates),
    selected_score=best_score,
    score_gap=best_score - second_score,
    market_regime=regime_code,
    target_turnover=target_turnover,
    actual_position_count=len(context.portfolio.positions),
)
```

还可记录各过滤器淘汰数量、空仓原因、止损原因、理论目标仓位和实际仓位。诊断数据用于解释参数为什么有效，不应只记录最终收益。

## 11. 自适应参数搜索

### 11.1 搜索循环

当前“预先生成全部组合再顺序运行”的模式，应逐步扩展为：

```text
propose → backtest → collect → evaluate → promote/stop → propose
```

搜索器只提出下一组参数，不直接操作 JQ；执行器只负责可靠运行，不决定什么参数更优；分析器只从已保存数据包计算指标。这样可以保持职责清晰，并允许替换搜索方法。

### 11.2 推荐阶段

1. **初始探索**：使用去重随机采样或拉丁超立方覆盖主要参数空间；
2. **低成本淘汰**：使用较短但有代表性的区间淘汰明显不合格参数；
3. **自适应搜索**：使用贝叶斯优化，根据已有结果提出更有信息量的参数；
4. **参数平台验证**：对高分区域的邻近参数补点；
5. **完整历史验证**：只晋级少量参数；
6. **独立区间验证**：最终候选运行真正独立的子区间回测。

### 11.3 鲁棒目标

不再只按全区间 Calmar 排序。可以使用可配置的综合目标，例如：

```text
robust_score =
    0.30 × 分区间 Calmar 中位数
  + 0.20 × 最差区间 Calmar
  + 0.15 × 分区间 Sharpe 中位数
  + 0.15 × 年度盈利比例
  - 0.10 × 区间表现离散度
  - 0.10 × 换手和成本惩罚
```

权重不是固定结论，需要写入实验配置。无论如何，目标函数至少应包含最差区间和稳定性惩罚。

### 11.4 参数平台

最终选择邻近参数也表现良好的区域，而不是最高分孤点：

```text
plateau_score =
    参数自身鲁棒得分
  + 邻域鲁棒得分中位数
  - 邻域得分标准差
```

如果不同参数产生高度相似的收益曲线、持仓和 `record()` 信号，应将它们聚为同一行为簇，减少重复回测，并用于估算有效独立试验数量。

### 11.5 停止条件

搜索预算应支持：

- 最大回测组数；
- 最大累计运行时间；
- 连续若干组没有实质改善；
- 候选区域不确定性已足够低；
- 只剩下与已有结果高度相似的参数；
- 所有候选都无法通过硬性风险门槛。

## 12. 鲁棒性和过拟合审计

### 12.1 一次长回测的区间切片

逐日收益可以切分为年度、季度、滚动窗口或市场状态，用于低成本稳定性筛选。这能减少为每个参数重复运行多个子区间回测。

但切片不完全等价于独立子区间回测，因为策略状态、预热期和之前持仓可能传递到后续区间。因此只对最终少量候选运行真正独立的子区间。

### 12.2 PBO

PBO（Probability of Backtest Overfitting）用于检查：样本内最优参数到了样本外是否经常跌到候选参数中位数以下。

它需要：

- 相同日期上的全部候选参数日收益；
- 保留表现差和失败的尝试记录；
- 多组时间块组合验证。

PBO 越低越好，但它不是未来亏损概率。

### 12.3 DSR

DSR（Deflated Sharpe Ratio）用于检查：在考虑多次参数尝试、样本长度、收益偏度和峰度之后，观察到的高 Sharpe 是否仍有统计可信度。

试验次数不能简单等于回测组数。相邻参数经常产生高度相关的收益，应根据收益曲线或交易行为聚类估算有效独立试验数量。

PBO 和 DSR 适合在一轮搜索结束后审计，不建议直接作为每次贝叶斯优化的唯一实时目标。

### 12.4 不能替代的验证

PBO、DSR 和参数平台都不能替代：

- 未来数据审计；
- 独立留出区间；
- 合理成本和成交假设；
- 对策略收益机制的人工判断。

## 13. 深入研究输出

对最终候选至少分析：

- 年、季、月和滚动窗口收益；
- 最差年度、亏损月份比例；
- 最大回撤持续时间和恢复时间；
- 下行波动和尾部损失；
- 参数间收益相关性和行为聚类；
- 佣金占收益比例、换手和连续亏损；
- ETF 选择、持仓集中度和标的贡献；
- 换仓后新旧资产收益差；
- 不同市场状态下的表现；
- PBO、DSR 和参数平台稳定性。

旧归档代码中的完整收益视图、持仓归因和换仓效果可按需迁移，但应先通过当前 JQ API 返回结构验证。

## 14. 文档生成

最终文档只从可追溯实验数据生成 Markdown，不把帖子声称或临时推测写成验证结论。

建议研究文档包含：

1. 原帖和作者引用；
2. 原策略逻辑摘要；
3. 源码审计结果；
4. 参数化和性能优化改动；
5. 原版与改造版等价验证；
6. 参数空间、搜索预算和停止条件；
7. 完整结果与鲁棒性分析；
8. PBO、DSR 和参数平台；
9. 局限、失败场景和未验证事项；
10. 策略代码 hash、回测 ID 和数据包索引。

文档初稿可以自动生成，但最终发布和外部分享保留人工确认。

## 15. 自动化边界

### 15.1 可以自动完成

- 帖子元数据收集和候选初筛；
- 原始源码 hash 和不可变留存；
- 静态审计和风险提示；
- 机械参数化和 YAML 初稿；
- JQ 冒烟回测、轮询、失败恢复；
- 参数提议、去重和预算控制；
- 回测数据包采集；
- 稳定性、PBO、DSR、持仓和订单分析；
- Markdown 研究文档初稿。

### 15.2 保留人工确认

1. **候选入库**：研究价值和源码使用范围；
2. **语义修改**：确认没有把原策略变成另一个策略；
3. **最终结论或发布**：确认样本外结果、局限和文字表述。

## 16. 推荐模块边界

避免为每个步骤创建只有一两个函数的浅模块。建议先形成四个较深模块：

| 模块 | 负责内容 |
| --- | --- |
| 候选工作流 | 候选台账、状态机、原始资产和人工门禁 |
| 策略适配 | 静态审计、参数化、性能优化和等价验证 |
| 实验引擎 | JQ 提交、轮询、恢复、任务身份和参数提议循环 |
| 结果研究 | 数据包采集、鲁棒性、归因和 Markdown 输出 |

现有 `executor.py` 可作为 JQ 平台适配基础，`optimize.py` 的参数生成逻辑可逐步迁入实验引擎，`analyzer.py` 和归档分析代码可作为结果研究模块的来源。

## 17. 分阶段实施

### P0：加固当前执行器

- 明确 `anchor_algorithm_id` 语义并支持配置覆盖；
- 保留当前真实 `Default_Back_Id` 作为兼容默认值；
- 完善实验任务指纹；
- 策略变更时自动创建新版本，不删除历史台账；
- 使用安全、原子的台账写入；
- 正式分析禁用隐式随机模拟指标；
- 完成后保存基础回测数据包。

### P1：跑通一个纵向切片

验收目标：

```text
一篇帖子 URL
→ 原始源码和候选清单
→ 自动审计
→ 参数化版本
→ JQ 默认参数冒烟回测
→ 基础回测数据包
```

先用一个代码完整、逻辑简单的 ETF 策略验证，不先做大规模社区抓取。

### P2：策略适配和等价验证

- 自动生成 `EXECUTION_` 参数和 YAML；
- 增加 JQ API 调用性能审计；
- 建立原版与改造版的收益、持仓、订单一致性检查；
- 保存 patch 和逻辑 hash。

### P3：自适应参数搜索

- 去重随机或拉丁超立方初始探索；
- 多阶段晋级和预算停止；
- 贝叶斯参数提议；
- 鲁棒综合目标和参数平台补点。

### P4：深度分析与文档

- 完整数据包分层采集；
- PBO、DSR、收益聚类和有效试验数；
- 持仓归因、换仓效果和成本分析；
- 自动生成 Markdown 研究初稿。

### P5：扩大社区发现

只有在 P1 至 P4 跑通后，再增加批量候选发现、自动评分和多策略横向索引。否则会先积累大量无法运行或无法相信的社区源码。

## 18. 总体验收标准

流水线达到可用状态时，应满足：

- 任意已入库候选都能追溯到原帖和原始源码；
- 任何生成策略都能说明相对原版修改了什么；
- JQ 锚点策略 ID 真实、稳定、可配置；
- 参数、逻辑、区间和成本变化不会错误命中旧回测；
- Notebook 中断后能够从台账恢复；
- 冒烟未通过的策略不会进入参数搜索；
- 搜索能够根据已有结果减少无价值回测；
- 最终选择来自稳定参数区域，而不是单一高分孤点；
- 所有研究指标都能回溯到回测数据包和回测 ID；
- 自动生成的文档清楚区分事实、推断、局限和未验证事项。

## 19. 核心结论

当前工程不需要推倒重来。最合理的演进路线是保留已有的参数注入、JQ 提交和分析能力，在其外层增加候选生命周期，在其内层加固实验身份与数据采集，再把静态批处理升级为可反馈的自适应搜索。

第一优先级不是批量抓取帖子，也不是立即引入复杂贝叶斯优化，而是跑通“一个候选策略从来源到 JQ 冒烟数据包”的纵向闭环。闭环稳定后，扩大候选规模和增加搜索智能才会真正降低手工成本，而不是放大不可追溯和过拟合问题。
